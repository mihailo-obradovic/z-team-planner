Every path above is relative to the directory holding this file — the Catalyst root here, `catalyst/` in a spawned project (`python3 tools/new_project.py`; details: `prime-directive.md`, Spawning Projects). That holds for the documents the project writes itself: `catalyst/features/`, `catalyst/decisions/`, `catalyst/experiments/`, `catalyst/context/`, never root-level directories. The generated root `CLAUDE.md`/`AGENTS.md` pointers and `.claude/skills/` wrappers are rewritten on spawn and upgrade — change the bundle documents, never them (`references/agent-skills.md`). For project work read that project's own `project-summary.md` and documents; the template's holds only writing guidance, and Catalyst's meta (`TODO.md`, `CHANGELOG.md`, `COVERAGE.md`, `VERSION`, `README.md`, `templates/`, `tools/tests/`, `.github/`) never travels into spawns.

## Non-Negotiables

- No implementation before the user approves the feature document or the decision record.
- A plan is implemented one step at a time, and no step is committed without the user's approval (`prime-directive.md`, Implementing A Plan).
- Behavior and its documentation change in the same commit (Same-Change Rule).
- Feature, decision, experiment, and non-`Minor` fix work runs on its own branch; merge back only after verification (`prime-directive.md`, Feature Branches).
- No bug fix without a root cause: reproduce or gather evidence first — never guess. A live system users depend on stabilizes first instead (`workflows/incident.md`).
- Never fabricate data to make code run: missing or unclear schema, token, or source → stop and ask; unavoidable placeholders are flagged loudly and recorded (Honest Inputs, prime directive).
- Documented protected areas are `Hard`: never change them without explicit user agreement; state the impact first.
- A dependency the stack modules in use do not already allow needs the user's approval and an `architecture.md` update in the same change (Dependency Change Rule, `architecture.md`).
- Follow the established architecture and style; keep changes narrow; never hide behavior changes in refactors.

Task weights, workflows, parallel work, and the review standard live in `prime-directive.md`.
