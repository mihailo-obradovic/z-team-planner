# Known Fakes Register (Example)

Worked example of `KNOWN_FAKES.md` for the fictional QA automation platform. Per the Known Fakes Register rule, a project carrying placeholder or synthetic data keeps one — a table row per fake: **What** (the fake, where it lives, where its loud runtime flag is emitted), **Why** (why real data was unavailable), **Removal** (the concrete condition that retires it). A project with no fabricated data has no such file.

| What                                                                                                                                              | Why                                                                            | Removal                                                                                                      |
| ------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------ |
| Six synthetic reviewer accounts seeded by `api/seeds/reviewers.py`; every login as one logs `SYNTHETIC ACCOUNT` and banners the UI session header | Staging IdP tenant not provisioned yet — no real reviewer identities to import | Delete the seed module and both flags once the staging tenant exists (`decisions/007_infra_staging_idp.md`)  |
| `fixtures/latency_baseline.json` — hand-written report timings; report footer prints `BASELINE IS SYNTHETIC` while it is loaded                   | No production traffic yet, and the report renderer needs a non-empty baseline  | Replace with the first week of recorded staging runs after launch, then drop the fixture and the footer flag |
